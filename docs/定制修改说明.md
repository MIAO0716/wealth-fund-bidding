# 定制修改说明（区分公司改成自己的竞标系统）

本说明写给想在本系统基础上改成**本单位自己的现场竞标系统**的区分公司，以及帮他们改代码的技术人员或 AI 编程助手。

按以下顺序进行：**先填需求登记表 → 判断哪些不用改代码 → 按修改位置表改代码 → 跑测试 → 打包部署 → 彩排**。

---

## 一、开始之前

### 1. 获取代码

- 代码仓库：<https://github.com/MIAO0716/wealth-fund-bidding>（目前为公开仓库）。
- 推荐用自己的 GitHub 账号 **Fork** 一份，之后在自己的仓库里修改、打包、发布，**不要直接改原仓库**。
- 不用 GitHub 的，可在仓库页面「Code → Download ZIP」下载源码。

### 2. 不能带走的东西

- **原活动的任何数据**：首轮数据、竞标流水、导出台账、数据库备份，这些都不在代码仓库里，也不要索取或拷贝。
- **原系统的云服务器和管理员账号**：区分公司要自己准备服务器，自己设置管理员密码。
- 代码仓库和安装包里**不含任何真实数据和密码**，可以放心使用。

### 3. 需要的环境（改代码的人）

| 工具 | 版本 | 用途 |
| --- | --- | --- |
| Node.js | 22.x | 构建与运行 |
| PostgreSQL | 16（14 以上均可） | 数据库，跑测试需要 |
| Git | 任意 | 管理代码 |
| Chromium / Playwright | 仓库已带依赖 | 端到端测试（可选） |

不会写代码也可以：把本说明和需求登记表交给 AI 编程助手（如 Claude Code），见第七节的提示词。

## 三、哪些不用改代码

以下内容在**管理端页面**就能设置，或者本来就不在系统里，**不需要改代码**：

| 内容 | 在哪里改 |
| --- | --- |
| 活动名称、活动日期 | 管理端「准备与配置」 |
| 各单位底标、首轮增幅 | 管理端「首轮数据」上传 Excel |
| 手机快捷档位（默认 +1/+5/+10） | 「准备与配置」→「其他设置」 |
| 高增幅二次确认阈值（默认 100%） | 「准备与配置」→「其他设置」 |
| 大屏是否显示金额 | 「准备与配置」→「其他设置」 |
| 会场 Wi-Fi（印在领导卡上） | 「准备与配置」 |
| 大屏声音开关、三种音效选择 | 「现场控制」→「大屏展示」 |
| KPI 计分、激励系数、容错规则 | **系统不计算分数**，会后由业务部门按台账核算；改这些规则只需改方案文件 |
| 服务器地址、端口、备份目录 | 服务器上的 `/etc/bidding/bidding.env`，见《云服务器部署》 |

如果区分公司只需要以上改动（单位、分组、门槛、项目名称都和原系统一样），**直接用原系统的安装包部署即可**，不用改代码。

## 四、需要改代码的地方

> 下表的路径都相对于仓库根目录。行号以当前版本为准，改之前先搜索确认。
> 系统的规则**前后端共用**：`packages/shared` 里改一处，手机端、大屏、管理端、服务端会一起生效。

### 1. 参赛单位与分组（最常见）

| 要改什么 | 位置 | 怎么改 |
| --- | --- | --- |
| 单位名称、单位代码、所属组别、显示顺序 | `packages/shared/src/units.ts` 的 `RAW_UNITS` | 每行一个单位：`['代码', '名称', 组号]`。代码用 2–4 位大写字母，全系统唯一，部署后不要再改 |
| 数据库里的单位表 | 新建 `apps/server/migrations/010_custom_units.sql` | 写法见下面的示例。**不要改 001–009 号旧文件** |
| 每组名称、最低增幅 | `units.ts` 的 `GROUPS` | `minIncreasePp: 10` 表示 10%，各组可以不同 |
| 界面上写死的「16 家」「32 行」 | `apps/web/src/pages/admin/FirstRoundTab.tsx`、`AccessTab.tsx`、`KdocsTab.tsx`，`apps/server/src/services/templates.ts`、`projects.ts`、`kdocs/admin.ts`、`kdocs/template.ts` | 搜索 `16 家`、`32 行`，改成实际数量，或改成按 `UNITS.length` 计算 |

`010_custom_units.sql` 示例（**只能在全新数据库、还没建任何活动时执行**）：

```sql
-- 替换参赛单位：××区分公司 12 家支行
DELETE FROM units;
INSERT INTO units (code, name, group_no, display_order) VALUES
  ('ZH01', '××支行', 1, 1),
  ('ZH02', '××支行', 1, 2),
  -- ……每家一行，与 units.ts 的 RAW_UNITS 完全一致
  ('ZH12', '××支行', 3, 12);
```

数据库表和 `units.ts` **必须一致**（代码、名称、组号、顺序），否则导入首轮时会报「未知单位」。

### 2. 组数不是 3 组

组数写死的地方较多，需要一起改：

| 位置 | 内容 |
| --- | --- |
| `packages/shared/src/units.ts` | `GroupNo` 类型（只允许 1、2、3）、`GROUPS` 数组 |
| `apps/server/src/services/projects.ts` | 约第 296 行 `[1, 2, 3].includes(groupNo)`、约第 463 行 `[1, 2, 3]` |
| `apps/web/src/pages/screen/ScreenPage.tsx` | 约第 785 行大屏顶部三组进度条 `[1, 2, 3]` |
| 数据库约束 | `units_group_no_check`、`projects_current_group_check`、`project_groups_group_no_check` 三个约束限制组号为 1–3：在 010 号迁移里 `ALTER TABLE … DROP CONSTRAINT …` 后按新组数重建 |
| 标王颁奖页 | `ScreenPage.tsx` 的 `AwardsScreen` 按「项目 × 组」排版，组数变化后要检查排版 |
| 测试 | `apps/server/test/bidding.test.ts`、`exports.test.ts` 等处循环 `[1, 2, 3]` |

### 3. 规则参数

| 要改什么 | 位置 |
| --- | --- |
| 标王门槛（默认 30%） | `packages/shared/src/rules.ts` 第 8 行 `CHAMPION_THRESHOLD_PP` |
| 加码最小单位（默认 1 个百分点） | `rules.ts` 第 4 行 `STEP_PP`；如改成 5 的倍数，服务端校验 `checkBidTarget` 也要加整除判断 |
| 默认快捷档位 | `rules.ts` 的 `DEFAULT_ALLOWED_INCREMENT_STEPS`（也可以在管理端改，不必改代码） |
| 只增不减、管理端下调更正 | 服务端 `apps/server/src/services/bids.ts` 和数据库触发器（007 号迁移）共同保证，**不建议改** |

### 4. 项目名称与顺序

| 要改什么 | 位置 |
| --- | --- |
| 项目显示名称（理财 → 存款等） | `packages/shared/src/units.ts` 的 `PROJECT_NAMES`、`parseProjectCode`（Excel 里按中文名识别项目） |
| 先后顺序 | `units.ts` 的 `PROJECT_ORDER`；`apps/server/src/services/projects.ts` 中「第一个项目锁定后手机自动切到第二个项目」的逻辑（搜索 `'wealth'`） |
| 页面上写死的「理财」「基金」文字 | 在 `apps/web/src` 和 `apps/server/src` 中搜索 `理财`、`基金` |

内部代码 `wealth`、`fund` **建议保留不改**，只改显示名称。代码同时出现在数据库约束、接口、导出文件中，改动面大，容易出错。

### 5. 项目数量不是 2 个（较大改动）

系统按「两个项目、依次进行」设计。改成 1 个或 3 个以上，需要改：

- 数据库：`projects_project_code_check`、`events_current_project_check`、`events_screen_project_check` 三个约束限定了 `'wealth', 'fund'`；
- `packages/shared/src/units.ts` 的 `ProjectCode`、`PROJECT_CODES`、`isProjectCode`、`parseProjectCode`；
- 服务端锁定后自动切换项目、导出 Excel、首轮模板，前端大屏结果页和颁奖页（`ScreenPage.tsx` 约第 648、780 行），手机端项目切换；
- 相关测试。

建议交给有经验的开发者或 AI 编程助手整体评估后再动手，并留出至少 2–3 天测试和彩排时间。

### 6. 文字、配色、声音

| 要改什么 | 位置 |
| --- | --- |
| 「全市合计」「全市增幅」 | `apps/web/src/pages/screen/ScreenPage.tsx` 约第 655、664 行 |
| 界面配色 | `apps/web/src/styles.css` 开头的 `:root` 颜色变量（`--red`、`--gold` 等） |
| 音效 | `apps/web/src/lib/sound.ts`（浏览器实时合成，不需要音频文件）；下拉选项名称在 `packages/shared/src/api.ts` 的 `BID_SOUNDS` 等 |
| 管理端输入框的示例文字 | `apps/web/src/pages/admin/EventPage.tsx`（例如活动名称的 placeholder） |

### 7. 金山文档通道

不用金山文档的，**不需要删代码**，管理端不配置就不会启用。要用的，按《金山文档接入说明》配置，其中「16 家单位文件」的文字也要按第 1 条一起改。

### 8. 配套文档

| 文档 | 位置 |
| --- | --- |
| 主持人讲话稿 | `docs/主持人讲话稿.md` |
| 领导使用指南 | `docs/领导使用指南.md` |
| 现场操作手册 | `docs/现场操作手册.md` |
| 竞标规则与流程（Word） | `docs/竞标规则与流程.docx`，由 `scripts/docs/gen-rules-docx.js` 生成：改脚本里的文字后运行 `node scripts/docs/gen-rules-docx.js 输出文件.docx` |

文档中的单位名称、分组、门槛、项目名称、全市目标都要同步改。

## 五、改完之后的检查（必须做）

在仓库根目录依次执行：

```bash
npm ci                       # 安装依赖
sudo service postgresql start  # 启动本机数据库（测试需要）
npm run typecheck            # 类型检查：改漏的地方大多会在这里报错
npm test                     # 单元测试
npm run build                # 构建前端和服务端
npm run test:e2e             # 端到端测试（先 build 再跑）
```

- 测试里有按原系统写死的断言（16 家单位、3 个组、浦东等单位名称），**改单位和分组后要同步改测试**，不要删测试。
- 全部通过后，再用「新建演示活动」在浏览器里完整走一遍：导入首轮 → 冻结 → 扫码 → 认领 → 各组加码 → 锁定 → 结果页 → 颁奖页 → 导出 Excel。

## 六、打包与部署

### 1. 用 GitHub 自动打包（推荐）

Fork 的仓库自带打包流程（`.github/workflows/`）：

1. 在自己仓库的「Actions」页面启用 Actions；
2. 运行「linux-package」（云服务器版）和/或「windows-package」（局域网版），勾选 `publish_release`；
3. 构建机会自动安装、测试，通过后发布到自己仓库的「Releases」页面。

### 2. 部署

- 云服务器：按 `docs/云服务器部署.md`，把下载地址换成**自己仓库**的 Releases 地址；安装时按提示设置**自己的**管理员密码。
- 局域网版（Windows）：按 `docs/部署说明.md`。
- 文档里出现的 `MIAO0716/wealth-fund-bidding` 地址，都要换成自己的仓库地址。

### 3. 上线前

- 正式活动前至少彩排一次（用演示活动，与正式活动完全隔离）；
- 管理员密码只告诉主控和联络两位工作人员；
- 正式活动前在「导出与备份」确认备份可用。

## 八、常见问题

| 问题 | 回答 |
| --- | --- |
| 只是单位名称不同、数量和分组一样，要改多少？ | 改 `units.ts` 的 `RAW_UNITS`，新建 010 号迁移，同步改测试里的单位名称和配套文档。约半天 |
| 已经部署过、建过活动，还能改单位吗？ | 不能直接改：数据库已有引用单位的数据。请在全新服务器（或清空后的新数据库）上部署新版本 |
| 能不能让单位和分组在管理端配置，不改代码？ | 当前版本不支持，属于功能开发。需要的话可作为新需求单独开发 |
| 计分、激励规则变了要改系统吗？ | 不用。系统只记录底标、首轮、加码和最终增幅，计分和激励在会后按台账核算 |
| 改完后原系统升级了，怎么同步？ | 在自己的 Fork 上用 GitHub 的「Sync fork」合并原仓库更新；与自己的修改冲突时，以保留自己的单位和规则为准逐个处理 |
