# 理财、基金现场竞标系统：开发需求与验收说明

版本：v1.0  
编制日期：2026-10-10  
用途：直接交给开发 Agent 实施。当前交付物为开发需求文档，不是已开发的软件。  
活动名称、年度、日期由管理员配置，不在代码中写死。

## 1. 给开发 Agent 的任务

开发一套可以正式运行的「领导手机 H5 竞标端 + 电脑实时大屏 + 工作人员管理端」网页系统，供上海市分公司16家区分公司参加理财、基金两个项目的现场竞标。

重点做到：领导操作简单、大屏清晰、数据实时同步、只增不减、按整数个百分点加码、首轮结果可后续导入、竞标结果可锁定和导出。

必须交付前后端、持久化数据库、部署说明和可执行验证。不能以静态页面、浏览器 localStorage、多标签页模拟或随机数据更新冒充多人实时系统。原型和演示数据可以有，但必须与正式活动隔离并标注「演示」。

实施时以本文的「已确定要求」为准；技术实现可以作合理调整。业务政策尚未明确的事项采用本文标注的保守默认展示，不擅自补充考核政策。不得阻塞开发；正式开启竞标前，必须在管理端检查必要配置。

## 2. 已确定要求与范围

| 项目 | 要求 |
| --- | --- |
| 参赛单位 | 16家区分公司，固定三个组别 |
| 竞标项目 | 理财、基金独立保存、独立排名，先理财后基金 |
| 竞标增幅基准 | 以本单位本项目的基础底标为基准 |
| 加码步长 | 1个百分点，单次追加为任意正整数个百分点，组内自由加码（方案 6.0） |
| 只增不减 | 首轮数据冻结后，领导端及工作人员代录均不得下调已确认增幅 |
| 首轮数据 | 后续提供，系统先实现导入接口、手动维护和独立展示页 |
| 数据同步 | 提交成功后，领导端、管理端、大屏展示一致的服务端数据 |
| 现场流程 | 基础底标确认、首轮展示、分组现场加码、项目锁定、两项目结果展示 |
| 竞标资格门槛 | 各组最低增幅均为10%（2027年一季度方案 6.0；此前为第一组5%、第二组10%、第三组15%） |
| 标王增幅门槛 | 30%及以上；每个项目每组独立判断 |
| 会前保密 | 完整首轮榜单默认不公开，由工作人员在会议现场主动发布 |
| 记录 | 保存每笔提交、操作人、来源、时间、前后增幅及回执 |

### 2.1 加码幅度的具体定义（2027 年一季度方案 6.0 调整）

每次加码为 1 个百分点的整数倍，组内自由加码：允许追加 +1、+2、+7、+12 等任意正整数个百分点；禁止 +0、+2.5、负数。手机端提供 −/＋ 微调和 +1/+5/+10 快捷按钮（快捷按钮只是便捷入口，可任意填写整数），默认 +1，主按钮显示「确认追加 +N 个百分点」。

例如基础底标100万元，当前增幅30%，追加3个百分点后为33%，竞标目标变为133万元。禁止按130万元再乘1.03计算。

所有申报增幅本身必须是整数百分点，且不低于所在组最低增幅（各组均为10%）。首轮导入同样执行此校验；如数据出现12.5%或8%，必须提示具体错误，不能自行取整或改值。

配置 `allowedIncrementSteps` 现在只决定手机端和代录窗口显示哪些快捷按钮（默认 `[1,5,10]`），服务端不限制必须是这些档位。

### 2.2 本期不做的业务

- 不自动结算活动结束后的KPI加分、业务激励或实际业务达标情况。
- 不自动决定未达目标后的标王递补；系统管理现场申报结果。
- 不接入客户信息、CRM、资金交易或产品销售系统。
- 不要求开发微信小程序、原生App或完整电子签章系统。

基础底标电子确认用于现场留痕；纸质签字备案可以通过导出台账完成。不能将点击「确认认领」宣传为具有特定法律效力的电子签名。

## 3. 分组与基础数据

单位稳定代码用于接口和权限绑定；单位名称用于展示，不能用名称模糊匹配。

| 组别 | 最低增幅 | 单位名称与代码 |
| --- | --- | --- |
| 第一组 | 10% | 浦东 PD、闵行 MH、宝山 BS、嘉定 JD、奉贤 FX、松江 SJ |
| 第二组 | 10% | 黄浦 HP、虹口 HK、静安 JA、普陀 PT、长宁 CN |
| 第三组 | 10% | 徐汇 XH、杨浦 YP、青浦 QP、金山 JS、崇明 CM |

两个项目代码：`wealth`（理财）、`fund`（基金）。每个项目16条初始竞标记录，合计32条。基础底标、首轮增幅都按「活动 + 项目 + 单位」存储，不能在项目间共用或串写。

基础底标暂未知，初始化为未填写；首轮增幅暂未知，初始化为未录入。缺失不等于0，不得替用户生成正式初始数值。可以提供单独的演示活动。

基础底标为正数金额。建议输入人民币万元，界面明确单位；数据库保存人民币分的整数或等价精确十进制，不采用浮点金额。竞标目标按人民币分四舍五入：

`竞标目标金额 = 基础底标金额 × (100 + 当前增幅百分点) ÷ 100`

若金额由API传递，统一使用十进制整数字符串，避免JSON大整数或浮点误差。大屏以万元展示，保留2位小数；排名只依据增幅，不依据显示金额。

正式启动前配置「业务指标名称、金额统计口径、统计周期、数据来源说明」，例如究竟是销量还是AUM净增，由组织者填写。系统不得自行把两者视为同一口径。

## 4. 页面、角色与访问方式

| 角色/页面 | 建议路由 | 可用功能 |
| --- | --- | --- |
| 领导手机端 | `/join`、`/bid` | 专属二维码进入，确认本单位底标，查看本单位首轮结果和当前增幅，向上追加，查看回执 |
| 首轮大屏 | `/screen/first-round` | 现场发布后，展示选定项目的16家首轮增幅、分组排名、数据完整性 |
| 实时竞标大屏 | `/screen/live` | 三组实时榜、首轮与当前增幅、加码动态、当前组别、竞标状态 |
| 最终结果大屏 | `/screen/results` | 理财、基金各三组锁定结果，展示候选/并列情况 |
| 工作人员管理端 | `/admin` | 配置、导入、校验、发布首轮、切换项目和组别、开始/暂停/恢复/锁定、代录、导出 |

### 4.1 手机访问和身份

- 管理员为16家单位生成专属二维码；同一单位二维码可在理财和基金切换时继续使用。
- 二维码含随机高强度一次性交换凭证，用于获取仅绑定本活动、本单位的会话。成功交换后从地址栏移除凭证。
- 默认一个有效单位会话，可由管理员重新发放二维码、撤销旧会话。多手机同时操作即使出现，也必须由服务端并发校验防止重复增加。
- 不允许用户通过选择下拉框或修改请求中的 `unitCode` 冒充其他单位。
- 会话有效期覆盖活动当天，活动锁定后不得提交；凭证、会话不能出现在公开大屏、日志和导出台账中。
- 大屏使用独立只读凭证，管理员使用独立登录。导入、代录、锁定、导出只允许管理员操作。

### 4.2 领导端界面

竖屏以一屏完成主操作，文字和按钮清晰，优先适配微信内置浏览器、iPhone Safari、安卓Chrome。不能依赖第三方登录完成竞标。

从上到下依次展示：

1. 本单位名称、组别、当前项目和状态。
2. 基础底标、会前首轮增幅、当前已确认增幅；当前增幅为最大视觉重点。
3. 底标未确认时显示「确认认领基础底标」，确认后保存项目级记录。
4. 追加选择：−/＋ 按 1 个百分点微调，或点 +1/+5/+10 快捷按钮，也可直接填写整数；默认 +1。
5. 预览追加后的增幅和竞标目标。
6. 主按钮「确认追加」，点击后二次确认，明确显示项目、单位、原增幅→新增幅、目标金额及「确认后不可下调」。
7. 提交后显示服务端成功回执；失败时展示明确原因。

只填写「追加多少个百分点」（正整数），不提供直接输入目标增幅、下调或撤销按钮。确认弹窗提交前可以调整。按钮应至少44px高，主操作建议56px。

成功后更新当前值、清除确认弹窗、防止双击；不自动连续追加。等待中、暂停、锁定、非当前组别、连接异常时，显示具体状态并禁用提交。

首轮数据未到时显示「首轮结果待录入」；不显示假0%。首轮尚未公开时，单位可看本单位数据，不得查看其他单位首轮榜单。

### 4.3 首轮结果展示

首轮是会前上报的数据，不等同于现场实时加码记录。必须有独立大屏页面或独立全屏模式，不能只在实时榜中藏一个小字段。

- 三组同时展示，第一组6家、第二组5家、第三组5家。
- 每行显示单位、首轮增幅、组内首轮排名；底标和目标金额可通过管理配置选择展示，默认大屏以增幅为主。
- 页头显示项目名称、首轮数据发布时间、完整性，如「16/16家已录入」。
- 允许开发阶段或管理预览展示缺失行，标注「待录入」，缺失行不参与排名。
- 正式发布和开启现场竞标要求该项目16家底标和首轮数据全部有效。
- 两项目的首轮数据可在管理端切换预览；在正式会议先展示理财首轮，基金首轮默认等理财锁定后再发布。
- 进入现场加码后，首轮快照保留不变；当前增幅从首轮快照起算。
- 可以随时回看首轮发布快照，不能因现场加码将首轮值覆盖。

会前管理预览仅管理员可看；投屏页面未发布时显示「首轮结果待现场发布」，不能调用公开接口泄露完整榜单。

### 4.4 实时大屏

以16:9、1920×1080为主要设计目标，同时适配常见投影比例。正式竞标时全部16家单位必须完整可见，不依赖滚动。

- 顶部：活动名称、理财/基金专场、当前开放组、运行/暂停/锁定状态。
- 中间：三个组别三列榜单；当前组突出，其他组保留数据但标注等待或已结束。
- 每行：排名、单位、首轮增幅、当前增幅。当前增幅比其他字段大，建议48px左右，单位名建议28px左右。
- 组头：最低增幅、达到30%门槛的领先单位；不足30%时显示「暂无符合门槛的标王候选」。
- 底部：最近5条追加记录和连接状态，如「浦东 理财 30% → 35%」。
- 加码后对单位行短暂高亮约2秒；领先变化给轻提示，不使用遮挡榜单的大动画。
- 默认声音关闭，可在现场明确开启。全屏按钮、字体对比度、字号适配必须验证。
- 不把KPI试算、开发信息、请求ID或内部错误堆在大屏上。

实时大屏和首轮大屏都应提供连接异常标识和最近同步时间；断线时保留最后一次已确认数据，清晰标注「连接中断，数据可能延迟」。

### 4.5 管理端

| 模块 | 要求 |
| --- | --- |
| 活动配置 | 名称、年度、日期、业务口径、二维码有效期、允许追加档位 |
| 单位管理 | 固定16家及分组，查看二维码状态，重发/撤销凭证 |
| 首轮数据 | 下载模板、上传CSV/Excel、JSON导入、手动录入、校验预览、整体提交 |
| 首轮发布 | 查看完整性，发布并冻结该项目首轮快照，切换大屏模式 |
| 现场控制 | 先理财后基金，当前组选择，开始、暂停、恢复、结束当前组、锁定项目 |
| 底标确认 | 查看各单位确认状态，允许工作人员按现场确认代记并注明原因 |
| 代录加码 | 仅可向上追加，与领导端同一校验、同一回执；必须填写代录原因 |
| 监控 | 大屏连接情况、单位会话/连接情况、提交失败记录 |
| 导出 | 首轮快照、最终竞标台账、追加流水、底标确认及项目锁定记录 |

允许开始、暂停等频繁操作保持简洁；项目最终锁定、首轮发布和正式数据重置属于重大操作，必须展示影响并二次确认。正式活动不提供一键清空，演示重置仅限演示活动。

## 5. 现场流程与状态控制

### 5.1 推荐运行顺序

1. 会前：配置活动和底标；导入后续提供的首轮数据；管理员检查32条记录及口径。
2. 领导扫码进入，查看本单位数据。基础底标按项目确认认领，允许等待阶段完成确认。
3. 现场：发布理财首轮，冻结快照并在大屏展示。
4. 开放理财第一组现场加码；依次第二组、第三组。大屏始终展示三组。
5. 各组结束后仍保留榜单；工作人员核对并锁定理财，产生不可修改的结果快照。
6. 发布基金首轮，按同样流程竞标并锁定基金。
7. 展示两项目六组结果，核对并列情况，导出最终台账用于公示、签字备案。

### 5.2 项目状态

| 状态 | 含义 | 是否允许加码 |
| --- | --- | --- |
| `DRAFT` | 底标/首轮可录入、修改、预览，未发布 | 否 |
| `ROUND1_PUBLISHED` | 首轮已发布且冻结，可认领底标 | 否 |
| `LIVE` | 正在现场竞标，仅当前开放组可提交 | 是 |
| `PAUSED` | 临时暂停，可展示数据 | 否 |
| `LOCKED` | 最终结果已锁定 | 否 |

合法状态转换：`DRAFT → ROUND1_PUBLISHED → LIVE ↔ PAUSED → LOCKED`。锁定只允许从暂停状态执行，便于核对；结束最后一组自动暂停。锁定不可退回。

组别状态：`WAITING / OPEN / CLOSED`；每个项目同时最多一个组 `OPEN`。关闭当前组时由服务端原子停止该组提交，再由管理员开放下一组。因现场调度需要重新开放已关闭组，只允许在项目未锁定且不存在其他开放组时由管理员操作，记录理由；原竞标增幅不能下调。

基金可以提前准备首轮数据，但理财未锁定前不可正式发布基金首轮或开启基金竞标。理财首轮冻结不会冻结尚未发布的基金草稿。

当前单位底标未确认，不允许提交加码；其他单位未确认不阻塞已确认单位的加码。开始本项目必须已发布完整有效首轮数据。

### 5.3 冻结与修改边界

- 首轮发布前：管理员可以修订底标和首轮草稿，每次写入留存变更记录。
- 发布时：原子冻结该项目完整16家底标和首轮数据，同时初始化当前增幅。
- 发布后：底标、首轮值不可覆盖或删改；现场追加不得修改首轮快照。
- 项目锁定后：领导和管理员均不得追加或改写锁定结果。
- 发布后如发现基础数据错误：暂停并导出记录，重新创建一场明确关联原活动的新活动，经组织者确认后重新发布；保留旧活动及原因。本期不开发绕过只增不减的“管理员任意修正”。

## 6. 排名、标王门槛与待定政策

### 6.1 可直接实现的排序

- 每个项目、每个组独立按当前申报增幅从高到低排名。
- 同增幅使用并列名次：例如30%、30%、25%显示1、1、3。
- 并列行内部按预设单位顺序排列，仅为稳定展示，不能以时间或单位顺序决定标王。
- 第一名增幅≥30%显示「标王候选」；若并列，所有符合条件第一名显示「并列领先·待确认」。
- 第一名不足30%显示「组内领先」，不展示标王称号。
- 锁定后显示「现场竞标结果」，与活动结束后的实际业务达标考核区分。

### 6.2 需要组织者确认的政策

| 未定事项 | 本期保守处理 |
| --- | --- |
| 并列第一如何授旗 | 标注并列；管理端提示组织者处理。可在锁定前重新开放该组组织追加，不自动认定唯一标王 |
| 现场标王能否被最终业务达标结果递补 | 本期不处理，保留现场记录供后续考核 |
| 无单位达到30%是否空缺 | 默认显示暂无符合门槛候选，不能绕过30%授予标王 |
| 单次追加幅度 | 已定（方案 6.0）：1 个百分点的整数倍，组内自由加码 |
| 是否有申报增幅上限 | 不擅设政策上限；异常大值要求更明确二次确认，技术整数范围不得冒充业务封顶 |
| 基础底标/达标口径 | 由管理端填写并确认；未配置不可正式开启 |

锁定动作允许保留并列事实，但必须提醒「本组并列第一，授旗规则未确认」。最终授旗展示仅对没有并列且达到30%的第一名展示「现场标王」；存在并列的组继续显示待确认。不能开发隐藏的人工指定第一名功能。

## 7. 首轮数据写入接口与模板

后续拿到数据时，应不需要修改代码就能录入。三种入口必须共用服务端校验：JSON接口、CSV/Excel上传、管理端手动录入。

### 7.1 导入字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `projectCode` | 枚举 | 是 | `wealth`或`fund` |
| `unitCode` | 枚举 | 是 | 本文16个单位代码 |
| `unitName` | 文本 | 否 | 有值时须与代码匹配，避免串单位 |
| `baseTargetWan` | 十进制字符串 | 是 | 基础底标，单位万元，必须>0，最多6位小数即精确到人民币分 |
| `firstRoundIncreasePp` | 整数 | 是 | 百分点数，30代表30%，不能传0.3或"30%" |
| `remark` | 文本 | 否 | 首轮来源或备注 |

CSV/Excel提供中文模板，列名：`项目、单位代码、单位名称、基础底标（万元）、首轮增幅（百分点）、备注`。项目允许「理财/基金」，服务端转换为固定代码。模板示范写30，不写0.3；Excel单元格使用普通数字格式，不用百分比格式。

可上传仅理财16行、仅基金16行、或两项目32行；也允许在草稿阶段逐批补齐。空白模板列出32个组合，底标和增幅留空；不能把演示值填进正式模板。

### 7.2 写入API

`POST /api/v1/admin/events/{eventId}/first-round/imports/validate`

```json
{
  "mode": "upsert",
  "rows": [
    {
      "projectCode": "wealth",
      "unitCode": "PD",
      "unitName": "浦东",
      "baseTargetWan": "100.00",
      "firstRoundIncreasePp": 30,
      "remark": "仅接口示例，非正式数据"
    }
  ]
}
```

以上100万元、30%仅解释字段；必须标为示例，不可作为正式初始数据。

校验返回：短期有效的 `validationId`、每行状态、错误原因、预览目标金额、将新增/修改的记录，以及导入后的项目完整性。验证结果绑定导入内容摘要、当前草稿版本和管理员，不能被替换内容后继续使用。

`POST /api/v1/admin/events/{eventId}/first-round/imports/commit`

```json
{
  "validationId": "返回的校验编号",
  "expectedDraftVersion": 3,
  "idempotencyKey": "客户端生成的唯一请求标识"
}
```

提交须重新核验权限、草稿版本、项目未发布和完整校验结果，在一个事务内写入该批次；任意一行错误则整批拒绝，不出现部分成功。默认 `upsert` 只更新本批指定记录，未提供记录保持原状；不支持通过漏传数据隐式删除。

校验要求：未知单位/项目、名称与代码冲突、同一项目单位重复、缺失必填、底标≤0、不合法金额精度、增幅非5整数倍、低于所在组最低增幅、已发布项目覆盖，均返回行级错误。系统不自动纠正、取整或忽略错误行。

手工录入也只修改草稿；批次提交成功后提供批次ID、时间、来源、操作者及版本。重复提交相同幂等键不能生成重复批次。

### 7.3 首轮发布API与读取

- `POST /api/v1/admin/events/{eventId}/projects/{projectCode}/publish-first-round`：带 `expectedDraftVersion` 和幂等键，检查16家完整有效、先理财后基金规则，冻结快照并发布。
- `GET /api/v1/admin/events/{eventId}/first-round`：管理员读取草稿及已发布快照。
- `GET /api/v1/screen/events/{eventId}/projects/{projectCode}/first-round`：大屏只读，仅返回已发布数据；未发布返回待发布状态，无榜单。
- `GET /api/v1/bidder/events/{eventId}/me`：仅返回当前会话单位的数据；会前不返回其他单位数据。

## 8. 现场提交接口与实时同步

### 8.1 提交追加

`POST /api/v1/bidder/events/{eventId}/projects/{projectCode}/bids`

```json
{
  "targetIncreasePp": 35,
  "expectedBidVersion": 4,
  "idempotencyKey": "每次点击确认时生成的唯一标识"
}
```

发送「最终确认增幅」而非单独发送增量；单位从认证会话读取，不信任请求自带单位。服务端计算差值，差值须为正整数。

同一事务内校验：

1. 会话有效，属于本活动、本单位；项目为当前专场。
2. 项目 `LIVE`，本单位所在组 `OPEN`，基础底标已确认。
3. `expectedBidVersion`等于当前版本。
4. 新增幅是整数、大于当前值。
5. 增幅满足组别底线（各组10%）。
6. 原子写入当前记录、递增版本、追加流水和同步事件。

成功响应至少返回：`bidId`、`unitCode`、`projectCode`、前后增幅、精确目标金额、`bidVersion`、`eventSequence`、`acceptedAt`。客户端以该回执显示成功，不凭按钮点击提前宣告成功。

### 8.2 并发、重复和锁定

- 幂等键在活动/主体作用域唯一，保存请求摘要及响应；相同键相同内容返回原结果，相同键不同内容返回冲突。
- 必须优先验证幂等历史再处理旧版本：已成功请求重试即使项目锁定，仍可查到原成功回执，不能误报再次加码或失败。
- 两部手机从30%同时提交35%，只允许一次成功；另一请求返回版本冲突及最新值，不可自动叠加成40%。
- 乐观版本冲突后更新界面并要求再次确认，不自动重试成新报价。
- 锁定和提交必须共享项目状态的事务互斥/行锁。锁定快照包含锁定事务之前已提交的记录，之后提交全部拒绝，不存在“已锁定后报价成功”。
- 项目锁定、组别关闭、暂停、首轮发布、管理代录都必须经服务端统一规则执行，不能靠前端按钮状态保证。

### 8.3 错误与回执查询

建议统一业务错误码：

| 代码 | 手机端提示 |
| --- | --- |
| `PROJECT_NOT_ACTIVE` | 当前项目尚未开放 |
| `PROJECT_PAUSED` | 竞标已暂停，请等待工作人员 |
| `PROJECT_LOCKED` | 本项目已结束，不能追加 |
| `GROUP_NOT_OPEN` | 尚未轮到本组，或本组已结束 |
| `BASE_NOT_ACKNOWLEDGED` | 请先确认认领基础底标 |
| `INVALID_STEP` | 追加后的增幅不符合规则（非整数或低于组别最低增幅） |
| `NOT_GREATER` | 新增幅必须高于已确认增幅 |
| `VERSION_CONFLICT` | 当前增幅已更新，请重新确认 |
| `IDEMPOTENCY_CONFLICT` | 请求标识冲突，请刷新并重新确认 |
| `SESSION_INVALID` | 会话失效，请联系工作人员重新扫码 |

提供 `GET /api/v1/bidder/events/{eventId}/requests/{idempotencyKey}` 查询本单位已提交请求。网络超时只能显示「结果待核验」，优先查询同一请求或用同一幂等键重试；未核实前不能创建新的加码请求。

管理代录单独使用 `/api/v1/admin/events/{eventId}/projects/{projectCode}/units/{unitCode}/bids`，增加 `reason`，但复用以上事务和校验。底标确认、暂停、恢复、开放/关闭组和锁定接口也需幂等和状态版本控制。

### 8.4 同步方案

推荐HTTP提交 + SSE推送；WebSocket可以替代。数据源为数据库，localStorage只允许保存界面偏好，不存权威竞标结果。

- 提供按权限裁剪的全量快照和事件流。领导只接收本单位状态及当前专场信息；大屏只接收已公开展示数据；管理员接收完整数据。
- 每个活动维护事务内递增的 `eventSequence`；消息包含序列、类型、项目、单位、服务端时间和相关版本。
- 首次加载：获取带序列的快照，然后订阅快照序列之后的持久事件，避免快照/订阅之间漏消息。
- 断线重连：根据最近序列补发；历史已不可补发则重新获取全量快照。
- 忽略重复和旧序列；检测缺口时重新同步。重启服务后能重建快照及补发记录。
- 每15秒心跳；超过约30秒未收到心跳显示断线。重连使用有限退避。
- SSE不可用时每2秒拉取最新快照作为降级方案；记录当前降级状态。
- 写入事务只发布已提交数据。推荐使用数据库事件表/outbox，避免数据库成功但推送丢失。

## 9. 推荐技术结构与数据模型

技术栈是建议，不限定版本。开发Agent应选用可维护、已验证的依赖并锁定实际使用版本，不引用未经检查的“最新版本”。

建议前端React + TypeScript + Vite，后端Node.js + TypeScript，数据库使用PostgreSQL。单服务进程、同域部署、服务端权威计算可满足16家现场竞标的规模；不需要微服务。若用其他栈，需提供同等事务、实时同步和部署能力。

建议仓库目录：`apps/web`、`apps/server`、`packages/shared`、`docs`、`tests`。共享类型、验证规则和错误码；后端校验不能依赖前端。

| 数据对象 | 核心字段/约束 |
| --- | --- |
| `events` | 活动配置、活动状态、演示标识、当前项目、全局序列 |
| `units` | 固定代码、名称、组号、展示顺序 |
| `projects` | 活动、项目代码、状态、草稿版本、控制版本、当前组、发布时间、锁定时间 |
| `project_groups` | 项目、组号、最低增幅、组状态 |
| `first_round_drafts` | 项目、单位、底标、首轮增幅、备注；组合唯一 |
| `first_round_snapshots` | 发布批次、冻结的16条底标及首轮值，不可变 |
| `bid_states` | 项目、单位、当前增幅、版本、底标确认状态；组合唯一 |
| `bid_records` | 前后值、目标金额、来源、操作主体、时间、回执，追加写入 |
| `import_batches` | 导入预览、内容摘要、草稿版本、来源、状态及操作者 |
| `idempotency_records` | 主体作用域、幂等键、请求摘要、响应，唯一约束 |
| `result_snapshots` | 项目锁定时完整16条结果、排名与并列信息，不可变 |
| `audit_logs` | 发布、导入、确认底标、代录、暂停、组切换、锁定等行为 |
| `realtime_events` | 持久序列、消息类型、数据及权限分类，用于补发 |
| `sessions` | 角色、活动、单位绑定、凭证哈希、到期及撤销状态 |

整数百分点例如35存为35，金额精确存储，时间存UTC并在界面按Asia/Shanghai显示。所有正式数据持久化；数据库迁移可执行，管理员密码和凭证不得硬编码。

## 10. 导出与现场运维

### 10.1 导出文件

至少支持.xlsx，另可提供CSV。Excel字段中百分比须正确格式化，例如底层0.35、显示35%，不能把35格式化成3500%。金额字段标明万元或人民币元。

| 工作表 | 字段 |
| --- | --- |
| 首轮结果 | 项目、组别、单位、基础底标、首轮增幅、首轮目标、发布批次、发布时间 |
| 最终竞标台账 | 项目、组别、单位、基础底标、首轮增幅、最终增幅、现场累计加码百分点、最终目标、组内排名、标王门槛/并列状态、锁定时间 |
| 加码流水 | 回执、项目、单位、前后增幅、追加百分点、目标金额、操作时间、领导/代录来源、代录原因 |
| 确认与控制记录 | 底标确认、首轮发布、暂停/恢复、组别开闭、项目锁定、操作主体与时间 |

备注等文本字段防止Excel公式注入，导出不含认证凭证。未锁定导出明显标为「过程数据」；最终公示台账来自锁定快照，不从可变页面状态取值。

### 10.2 部署与网络

支持两种部署，并给出完整说明：

- 互联网HTTPS部署：电脑投屏和领导手机访问同一域名，推荐正式使用；需验证会场手机和电脑网络可访问。
- 会场局域网部署：电脑/小型服务器运行后端和数据库，手机加入同一可达Wi-Fi；确认AP隔离关闭、端口可达、IP固定或稳定域名、证书与移动浏览器兼容。不能将电脑localhost二维码发给手机。

二维码地址使用配置的实际对外地址，而不是客户端猜测。生产构建尽量自托管字体和静态资源，避免现场依赖外部CDN。

需要交付 `.env.example`、数据库初始化/迁移命令、管理员初始化、开发/构建/运行命令、容器部署示例和健康检查。反向代理须正确支持SSE长连接并关闭缓冲。

提供备份/恢复操作说明，至少在首轮发布后及项目锁定后生成可恢复检查点；服务重启数据完整。恢复备份需在停写状态下执行并保留恢复记录，防止仍存旧会话继续报价。

断网处理：领导端停止提交，不离线排队；工作人员口头记录经领导确认的目标，网络恢复后按真实目标差额一笔代录（差额为整数即可），遵守状态校验并记录现场实际确认信息，不能制造虚假原始发生时间。后端不可用时大屏只展示最后快照并提示异常，不能在电脑本地虚构成功。

## 11. 验收场景

| 编号 | 操作 | 必须看到的结果 |
| --- | --- | --- |
| A01 | 正式活动未提供底标/首轮 | 显示待录入，不能发布或开始；无随机正式数据 |
| A02 | 导入各组 10%（各组最低增幅） | 校验通过；首轮和目标正确 |
| A03 | 导入12%、第二组5%、第三组5% | 分别提示非5倍数或低于组别门槛（10%），整批不写入 |
| A04 | 导入重复单位、错名称、未知代码、非法底标 | 行级报错，无部分成功 |
| A05 | 同时导入理财和基金32条 | 数据独立；同一单位两项目底标可不同 |
| A06 | 草稿导入成功但尚未现场发布 | 管理员可预览；大屏不泄露完整榜单；单位只看自己 |
| A07 | 发布理财首轮 | 展示16家三组首轮榜；冻结快照，当前增幅从首轮起算 |
| A08 | 30%选择+5后确认 | 服务端得到35%，目标按底标×1.35；大屏跟随更新 |

| A10 | 篡改请求提交32%、30%、25%或不允许差值 | 服务端拒绝，不只依靠前端限制 |
| A11 | 首轮30%，现场追加到40% | 首轮页仍30%，实时页40%，累计加码10个百分点 |

| A14 | 成功但响应丢失，随后项目锁定 | 回执查询仍能确认原成功；不再次加码 |
| A15 | 锁定与加码并发 | 结果符合事务先后；锁定后无新成交记录 |
| A16 | 暂停、非当前组、底标未确认提交 | 均按对应原因拒绝 |
| A17 | 浦东改请求冒充闵行 | 无法替其他单位报价或读未公开资料 |
| A18 | 理财未锁定时开启基金 | 拒绝；理财锁定后基金可以发布和开始 |
| A19 | 同组最高25% | 显示组内领先，无标王候选 |
| A20 | 同组两家35%、第三家30% | 名次1、1、3；并列待确认，无自动唯一标王 |
| A21 | 大屏断线20秒后重连 | 恢复完整当前结果，不漏报、不重复叠加；首轮值不变 |
| A22 | 服务重启 | 底标、首轮、当前增幅、状态、回执、锁定结果均保留 |
| A23 | 管理员代录 | 同等校验，标明代录来源与原因，不能下调 |
| A24 | 两项目锁定并导出 | 32条最终台账可核对，首轮与流水一致，无凭证泄露 |
| A25 | 手机与1920×1080大屏实测 | 手机上两步确认提交，16家大屏完整可读，无横向溢出 |

验收必须包含真实不同设备/浏览器会话，不只在同一浏览器切标签页。建议至少：2部手机、1个管理浏览器、1个大屏浏览器，并测试同单位并发。

性能参考目标：在部署网络正常情况下，16个领导会话、2个大屏、1个管理端并发使用，报价成功后大屏更新通常≤1秒，95%≤2秒；网络故障时明确显示延迟/断线。通过服务端提交时间与大屏应用时间测量，不能只口头宣称实时。

关键自动化测试应覆盖：门槛/步长、导入事务、身份越权、幂等、并发、锁定竞态、首轮冻结、项目隔离、事件补发和状态切换。UI测试覆盖完整双项目流程和失败提示；不必为纯装饰组件大量编写测试。

## 12. 开发交付与推进顺序

### 第一阶段：数据和规则

建立16家单位与两个项目；实现数据库、认证、底标及首轮草稿、导入预览/提交、发布冻结、状态机、步长校验、加码事务、幂等与日志。

### 第三阶段：正式使用准备

完成锁定快照、最终结果、Excel导出、备份恢复、部署文档，跑完验收场景，进行两项目全流程彩排。

### 最终必须交付

- 完整源代码、锁定的依赖、数据库迁移和正式构建产物说明。
- README：本地启动、生产部署、二维码配置、访问角色、演示/正式隔离方式。
- 空白首轮数据模板（32行）及接口文档/请求示例；示例数据单独标为演示。
- 可操作的手机、首轮大屏、实时大屏、结果大屏、管理端。
- Excel导出与备份/恢复说明。
- 测试命令、实际执行结果和已知限制。
