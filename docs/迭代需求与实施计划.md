## 1. 目标与已确认条件

### 1.1 核心目标

领导开启手机流量，使用微信“扫一扫”扫描本单位专属二维码，直接在微信内进入本单位竞价页面，完成底标确认、报价及回执查看。工作人员管理活动，现场大屏同步显示竞价状态和结果。

目标操作路径：

> 手机流量 → 微信扫一扫 → 自动验证单位凭证 → 本单位竞价页 → 确认报价 → 查看回执

领导无需复制网址、切换外部浏览器、安装额外软件、连接会场 Wi-Fi，或登录 NAS、穿透服务账户。外网地址由工作人员配置并写入二维码。

## 4. 已确认缺陷与修复要求

### FIX-01 / P1：消除失败写请求的连接池互等

**场景与问题**：并发写请求进入失败记录分支时，`runWrite()` 回滚后继续持有事务连接，再由 `recordFailure()` 申请新连接。连接池被占满时，请求可能互相等待，健康检查和正常操作也被阻塞。

**位置**：`apps/server/src/services/context.ts`、`apps/server/src/db/pool.ts`。基线连接池上限为 20。

**实施范围**：调整失败记录和连接释放顺序，确保失败路径不嵌套等待额外连接。优先评估复用回滚后的连接，或释放后再写失败记录；实现时保证单次释放、原始业务错误和失败审计语义正确。

**验收标准**：

- [ ] 先保留可复现旧行为的用例，再完成最小修复。
- [ ] 独立 PostgreSQL 测试库中，以连接池容量及以上的并发失败请求验证所有请求在测试超时内完成。
- [ ] 测试后连接池可继续处理正常写入和健康检查，没有连接泄漏、重复释放或未结束事务。
- [ ] 失败记录自身异常时，错误可诊断，且不会导致请求永久等待。

### FIX-02 / P1：恢复失败必须明确终止

**场景与问题**：Windows、Linux 打包恢复脚本将 `pg_restore` 非零退出码作为警告后继续运行，可能对部分恢复的数据库提示成功；Linux 路径还会启动应用。

**位置**：`packaging/windows/scripts/restore.ps1`、`packaging/linux/scripts/bidding`。`scripts/restore.sh` 的行为应独立核对，避免把不同脚本视作同一缺陷。

**实施范围**：评估并采用事务恢复及失败退出；明确“备份当前数据 → 停止业务写入 → 恢复 → 校验 → 作废旧访问凭证 → 开放服务”的顺序。失败时保持业务不可写，保留恢复前备份及错误记录。数据库本身须保持可供恢复工具访问。

**验收标准**：

- [ ] 覆盖可读取备份目录、但实际恢复发生权限、约束或数据错误的场景。
- [ ] 任一恢复或后置校验失败，脚本返回非零退出码，无成功提示，应用不会自动恢复写入。
- [ ] 完整恢复成功后，校验活动、单位、报价、结果快照及审计记录之间的一致性。
- [ ] 旧领导会话、大屏会话及未使用二维码按既有恢复规则失效；工作人员重发后可正常进入。
- [ ] 在隔离数据库中实际恢复一次，并保存命令退出码和校验结果。Windows/Linux 在其各自环境验证。

### FIX-03 / P1：管理员密码重置同步撤销会话

**场景与问题**：`createAdmin()` 更新密码后，原管理员 Cookie 仍可能在有效期内执行操作。

**位置**：`apps/server/src/services/auth.ts`，以及调用管理员重置逻辑的 CLI/打包入口。

**实施范围**：在同一事务中更新密码并撤销该管理员的全部有效会话；接入 FIX-04 的实时连接撤销。保留首次创建管理员行为。

**验收标准**：

- [ ] 重置前登录，重置后使用旧 Cookie 调用管理接口被拒绝。
- [ ] 旧密码登录失败，新密码登录成功；其他管理员会话不受误撤销。
- [ ] 密码更新或撤销操作失败时整体回滚。
- [ ] CLI、Windows 和 Linux 入口调用的行为一致；日志不包含明文密码或 Cookie。

### FIX-04 / P2：SSE 连接与访问权限同步失效

**场景与问题**：实时连接只在建立时鉴权；会话撤销或到期后，已建立连接可能继续接收事件。

**位置**：`apps/server/src/routes/sse.ts`、`apps/server/src/services/realtime.ts`、相关认证与撤销入口。

**实施范围**：订阅绑定必要的会话/凭证身份及有效期；撤销时关闭对应订阅，到期时停止推送；重新连接重新鉴权。实现应覆盖管理员、单位和大屏的各自认证机制。

**验收标准**：

- [ ] 撤销事务成功后触发的新业务事件，不再向相应旧订阅发送有效载荷。
- [ ] 到期时终止推送；定期复核的时间窗口在实现中明确并纳入测试。
- [ ] 管理员重置密码、单位换手机、退出登录及大屏撤销场景分别通过。
- [ ] 重连不能绕过鉴权；无关单位、活动和管理员连接继续工作。

### FIX-05 / P2：请求超时覆盖响应正文

**场景与问题**：前端收到响应头后即清理计时器，正文读取停滞时可能长期显示提交中；正文读取异常也未统一转换。

**位置**：`apps/web/src/lib/api.ts`。

**实施范围**：让超时覆盖网络请求与正文读取，统一错误转换，在结束路径清理计时器。保持已有 `ApiError` 与结果待核验约定。

**验收标准**：

- [ ] 模拟响应头已到达、正文不结束，仍能按配置超时终止。
- [ ] 正文中途断开、普通网络错误、业务错误、正常响应分别得到正确处理。
- [ ] 报价响应丢失时显示“结果待核验”，通过原请求标识核验服务端结果，避免误报失败或重复报价。
- [ ] 请求结束后没有遗留计时器或长期 loading 状态。

## 5. 功能、部署与运维迭代

### DEP-01 / P1：群晖容器部署可重复执行

**使用者目标**：工作人员可以在 DS920+ 上按文档部署、备份、重启和升级系统。

- 沿用 `Dockerfile` 和 Compose 中应用、PostgreSQL 两个服务；按实际群晖环境安装兼容的 Container Manager。
- 明确项目、配置、数据库和备份的位置；验证数据库卷持久化及应用容器对备份目录的写权限。
- 确认 NAS 剩余内存、其他任务负载、镜像拉取和构建条件；必要时在其他机器构建兼容镜像后导入。
- 校验 `DATABASE_URL` 中密码特殊字符的编码方式，提供能实际运行的配置示例；示例不包含真实密码。
- 提供启动、健康检查、日志查看、备份、恢复、升级及失败回退步骤；涉及数据库迁移时说明回退兼容边界。
- 记录镜像或版本标识，测试应用、数据库、穿透进程的重启恢复行为。

**验收标准**：

- [ ] 按新文档从干净配置部署成功，健康检查正常，管理端可登录。
- [ ] 应用/数据库容器重建和 NAS 重启后，已提交数据仍在，服务可以恢复。
- [ ] 真实生成备份文件，并在隔离数据库恢复成功。
- [ ] 外部仅发布应用所需入口；数据库、NAS 管理接口不因项目部署额外公开。
- [ ] 保存 NAS 资源占用和部署版本记录，形成容量判断依据。

### DEP-02 / P1：提供微信可直接访问的 HTTPS 外网入口

**使用者目标**：领导使用手机流量，微信扫码直接进入竞价页面。

**实施内容**：

- 评估穿透服务提供的固定 HTTPS 子域名，或自有域名配合穿透/公网转发；最终选择依据为微信实测、网络质量、SSE 支持及服务条件。
- 选择活动期间持续有效的地址，配置 `PUBLIC_BASE_URL` 和安全 Cookie，再生成正式二维码。
- 穿透与反向代理保持路径、凭证交换、Cookie 和流式响应正常；关闭 SSE 响应缓冲，配置合适的长连接超时。
- 仅在应用处于可信代理之后时启用相应 `TRUST_PROXY` 配置，并验证转发头处理。
- 外网入口不增加领导必须完成的第三方登录、下载客户端、复制网址或跳转外部浏览器步骤。
- 明确二维码地址变更的处理流程：重新配置并重新发放，旧打印卡回收。正式活动期间冻结地址。

**验收标准**：

- [ ] iPhone、安卓各至少一台，关闭 Wi-Fi，使用正式入口生成的二维码在微信中扫码。
- [ ] 首次扫码自动显示正确单位和组别；在微信内完成底标确认、报价、回执查看。
- [ ] 验收过程中不依赖复制链接、外部浏览器或 NAS/穿透服务账户登录。
- [ ] 验证预期使用的运营商网络；至少覆盖两种运营商，并记录未覆盖范围。
- [ ] 连续运行覆盖预计活动时长，实时连接及备用轮询正常；没有事件集中延迟到连接结束才显示的情况。
- [ ] 若微信对入口出现阻断、强制外跳或额外中转，判定入口验收未通过，调整入口后重新测试。

**边界**：普通浏览器能打开、HTTPS 证书有效、已经购买域名，都不能单独证明微信扫码验收通过。无需将微信小程序或微信身份授权设为本轮前置条件。

### UX-01 / P1：完善领导端微信使用闭环

**使用者目标**：领导能清楚知道当前单位、报价金额、提交结果和下一步操作。

**实施内容与验收标准**：

- [ ] 核对 `/join` 的首次扫码、同一有效会话再次扫码、过期/已用/撤销凭证提示。
- [ ] 将“绑定手机”的操作说明准确表述为有效浏览器会话；同一手机切换浏览器、清理微信数据等情况按换设备流程处理，避免宣称硬件级绑定。
- [ ] 二次确认时固定展示本次准备提交的单位、项目、增幅、金额和版本；期间数据变化时重新确认，保证实际提交与所见一致。
- [ ] 区分提交中、成功回执、明确拒绝、结果待核验；结果不明时保留原请求标识和原参数。
- [ ] 明确待核验状态在刷新、关闭页面、微信切后台后如何恢复；复用既有会话及回执查询，避免创建重复业务请求。
- [ ] 微信切后台、锁屏、来电后返回可重新同步；展示断线或旧数据状态，提交仍由服务端校验版本与权限。
- [ ] 管理员换手机操作后，原会话失效，新二维码可进入，历史报价保持不变。

### UX-02 / P2：管理端操作具备结果核验能力

**使用者目标**：工作人员在代录、底标代记、开始/暂停/恢复及锁定响应丢失时，能确定操作结果。

**位置**：`apps/web/src/pages/admin/ControlTab.tsx` 及对应服务端请求记录接口。

**实施内容与验收标准**：

- [ ] 参考领导端现有机制，为同一业务操作保留原幂等键与请求内容。
- [ ] 先核对服务端已有请求查询覆盖范围；仅对缺失的操作补充最小接口。
- [ ] 响应丢失后显示待核验，并能查询成功或失败结果；人工重试复用原请求，新的业务动作使用新标识。
- [ ] 模拟服务端已提交但客户端未收到响应，重试后业务记录仅产生一次。
- [ ] 代录成功显示单位、项目、增幅和回执；控制操作显示已执行动作及最新状态。

### OPS-01 / P2：会前与锁定前检查可操作

**使用者目标**：工作人员在开始或锁定前，一次看到需要处理的事项。

**实施内容与验收标准**：

- [ ] 在现有会前检查中汇总配置、首轮数据、二维码发放、单位进入情况、底标认领及最近备份状态。
- [ ] 锁定预览汇总未认领单位、未结束组、待处理并列、代录记录，以及系统可识别的待核验事项；不能宣称掌握未上报的客户端状态。
- [ ] 每条异常包含单位/组别、原因和处理入口，避免只有笼统警告。
- [ ] 明确哪些事项只是提醒、哪些阻止开始或锁定；这项业务政策由组织者确认后实现。
- [ ] 保留现有金额计算、排序、并列处理及项目推进规则，变更规则须单独确认。

### OPS-02 / P2：备份状态可见，恢复结果可验证

**使用者目标**：工作人员能知道最近一次备份是否成功，必要时能恢复已验证的数据。

**实施内容与验收标准**：

- [ ] 在既有自动检查点基础上展示未配置、进行中、成功、失败状态及最近成功时间。
- [ ] 失败显示可执行的处理建议；部分生成的文件不能标记为成功备份。
- [ ] 明确保留策略和可用空间检查方式，保存一份不依赖同一 NAS 存储故障域的备份副本。
- [ ] 在独立测试库完成恢复演练，记录备份标识、校验结果、耗时和恢复后的业务状态。
- [ ] 明确数据可恢复到哪个检查点，记录该检查点后的数据损失范围，避免承诺未实现的零数据丢失。

### OPS-03 / P2：监控信息支持现场处理

**使用者目标**：工作人员能判断异常来源并按步骤处理。

**实施内容与验收标准**：

- [ ] 基于现有监控页展示应用/数据库健康、单位最近活动、实时连接状态和最近备份结果。
- [ ] 区分断线、会话失效、组未开放、活动暂停、版本冲突和待核验；在线状态注明时间及判断依据。
- [ ] 为异常提供重发二维码、核验回执、检查外网入口等操作建议。
- [ ] 诊断记录可关联活动、单位、操作和时间；导出或日志不暴露完整凭证、密码和 Cookie。

### ENG-01 / P2：建立提交级持续验证

**使用者目标**：后续修复能够重复验证，避免已解决的问题再次出现。

**实施内容与验收标准**：

- [ ] 在现有打包工作流之外，补齐普通提交和 PR 的类型检查、构建、规则测试和服务端集成测试。
- [ ] PostgreSQL 集成测试使用独立测试库，显式配置连接；不得指向生产数据库。
- [ ] 基于现有 Playwright 场景补充报价响应丢失、幂等重试、会话撤销、锁定边界和重新扫码用例。
- [ ] E2E 使用独立数据库；其准备脚本会清理数据，执行前校验目标库。
- [ ] 测试失败时保存必要的日志、截图或 trace，并防止测试产物带入真实凭证。
- [ ] Docker 冒烟验证启动、健康检查及基本业务；Windows/Linux 恢复脚本在适用平台验证。
- [ ] 自动化浏览器测试与微信真机验收分别记录。

## 6. 建议性能目标与验证方法

以下数字用于制定测试计划，属于建议值，尚未经用户确认，也不代表当前系统已经达到。正式验收前结合活动时长、网络和 NAS 负载确定。

| 指标 | 建议目标 | 测量方法 |
|---|---|---|
| 业务规模 | 16 家单位终端 + 2 个管理会话 + 1 个大屏 | 按实际操作节奏彩排 |
| 扫码首屏 | 可用移动网络下，P95 ≤ 5 秒 | 从微信识别二维码到单位信息可操作 |
| 报价回执 | 可用移动网络下，P95 ≤ 2 秒 | 点击最终确认到显示服务端回执 |
| 大屏同步 | 正常 SSE 下 P95 ≤ 2 秒 | 从服务端接受报价到大屏显示 |
| 网络恢复 | 恢复可用网络后 10 秒内同步最新状态 | 断网、切后台和恢复测试 |
| 持续运行 | 预计活动全程，再增加 30 分钟观察 | 记录资源占用、错误和重连次数 |
| 数据正确性 | 重复请求不重复记账；回执与数据库、导出一致 | 相同幂等键重试并核对记录 |

性能统计记录设备、运营商、时间、样本量、入口服务、应用版本、NAS 资源占用和异常情况。业务规则拒绝与网络/系统失败分开统计。连接池耗尽测试应额外覆盖池容量及以上并发，不能只做常规 16 终端演示。
